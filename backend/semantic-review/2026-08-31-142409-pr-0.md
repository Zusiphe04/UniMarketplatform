# Split IntelliJ seed workflow for the complete UniMarket lifecycle

The monolithic seed script is replaced by eleven manually executed IntelliJ HTTP files covering six identities, vendor approval, products, reporting, events, checkout, simulated payments, reviews, escrow, engagement, notifications, and authentication sessions. The routes, methods, headers, bodies, enum literals, public detail endpoints, and credential-free payment shape match the current backend. Tracing the services reaches the verifier’s intended state: three orders, four payment attempts, inventory of 4/0, paid/released/refunded order outcomes, buyer/seller points of 23/24, one retained cart row, and zero active buyer refresh sessions. The remaining defects are in the manual handoff documentation.

**Watch for:** **confirmed** — access JWTs last only 15 minutes but are reused across distant files without a renewal checkpoint; **confirmed** — the two payment-attempt UUID placeholders have no documented response handoff; **confirmed** — legacy `ORD-*` and `request 95` labels disagree with the current backend and split workflow.

**Verdict**: NEEDS_CHANGES

## High-level view

The workflow deliberately exposes tokens and UUIDs as `PASTE_*` variables, but the pasted JWTs can expire before later files use them. The administrator token created at the start is expected through file 09, the buyer token through file 11, and the post-approval seller token through file 10 despite a 15-minute access-token lifetime.

Most generated identifiers have a guide-level source. Payment attempts are the exception: file 07 requires `declinedPaymentId` and `successfulPaymentId`, but neither the file nor the guide identifies the simulation response `id` to paste.

The order-ID guidance retains two legacy labels. The backend generates `UM-*` references rather than `ORD-*`, and the split, unnumbered workflow no longer has a meaningful “request 95.”

## Fifteen-minute JWTs do not cover the documented phase handoffs

**Confirmed.** `src/main/resources/application.properties:36` sets the access-token lifetime to `PT15M`. File 01 produces the administrator, resident, and buyer tokens used as late as files 09, 05, and 11, while the fresh seller JWT from file 02 remains a prerequisite through file 10. The guide has no expiry, refresh, or re-login checkpoint, so a manual run crossing 15 minutes receives `401` responses even when every UUID handoff is correct.

The refresh cookie cannot renew every identity because successive logins on `localhost:8080` replace the single `unimarket_rt` cookie in IntelliJ’s shared cookie jar. Add a token-lifetime note and visible re-login checkpoints before later files that need administrator, buyer, resident, or seller credentials, then instruct the operator to update the corresponding token variable. This preserves the required manual copy model without response scripts.

## Payment-attempt detail prerequisites have no source instruction

**Confirmed.** `http/seeding/07_payments.http:11-12` declares `declinedPaymentId` and `successfulPaymentId`, then lines 79 and 84 consume them. `SEEDING.md:98` omits payment IDs from its generated-ID copy list, and file 07 does not annotate either source response. Add “payment” to the guide’s list, then identify the declined SnapScan response `id` and successful PayFast retry response `id` as the values to paste; naming PayFast removes ambiguity among three successful simulations.

## Legacy reference labels conflict with the current split workflow

**Confirmed.** `MarketplaceOrderFactory.java:25` generates `UM-*` references, while `SEEDING.md:98`, `06_cart_checkout.http:2`, and `07_payments.http:4` call them `ORD-*`. Replace all three stale prefixes; the accompanying instruction to use `OrderResponse.id` remains correct.

**Confirmed.** `scripts/verify-seed-data.sql:378` says buyer sessions disappear “after request 95,” but the new files expose no absolute request numbering. Replace it with “after the final logout-all request.”
